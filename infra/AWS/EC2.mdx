# EC2란?

EC2는 **Amazon EC2 (Elastic Compute Cloud)**의 줄임말로,
AWS에서 제공하는 가상 서버 서비스입니다.

- Virtual Machine
- 재구성이 가능한 컴퓨팅 리소스
- 쉽게 확장/축소되는 컴퓨터 용량
- 고객 업무 영역에 따른 다양한 인스턴스 타입 제공
- 사용한 만큼만 과금 (pay-as-you-go)

> EC2는 단일 서비스가 아니라 가상 머신 임대(EC2), 가상 장치에 데이터 저장(EBS), 머신 간 부하 분산(ELB), 자동 확장 그룹(ASG)을 통한 서비스 확장까지 포함하는 개념입니다.

### EC2에서 설정할 수 있는 항목

- **OS**: Linux, Windows, Mac OS
- **CPU**: 컴퓨팅 성능 및 코어 개수
- **RAM**: 메모리 크기
- **스토리지**: 네트워크 연결(EBS, EFS) 또는 하드웨어(EC2 Instance Store)
- **네트워크 카드**: 속도 및 공인 IP 주소
- **방화벽**: 보안 그룹(Security Group)
- **부팅 스크립트**: EC2 User Data

### EC2 User Data

인스턴스가 **부팅될 때 실행되는 스크립트**로, 초기 설정을 자동화합니다.

- **Bootstrapping**: 머신이 처음 시작될 때 명령을 자동으로 실행
- 인스턴스가 처음 시작될 때 **한 번만 실행**되며, 이후 재부팅되어도 재실행되지 않음
- **루트 계정 권한**으로 실행됨
- 부팅 시에만 사용 가능하며, 인스턴스 시작 후에는 수정 불가
- 암호화되지 않은 텍스트로 저장되므로 **민감한 정보(비밀번호, 키 등)를 넣으면 안됨**
- 주로 업데이트 설치, 소프트웨어 설치, 파일 다운로드 등 초기 설정 자동화에 사용

### 인스턴스

인스턴스 이름은 `m5.2xlarge`처럼 **[클래스][세대].[크기]** 형태로 지정됩니다. (m: 인스턴스 클래스, 5: 세대, 2xlarge: 크기)

- 범용 (M4): 컴퓨팅, 메모리 네트워크 리소스의 균형적 사용 -> 웹 서버, 코드 리포지토리 등 다양한 작업에 적합
- 컴퓨팅 (C4): EC2에서 최고 성능의 프로세서, 성능 대비 저렴한 가격 -> 배치 처리, 미디어 트랜스코딩, HPC, 머신러닝, 게이밍 서버
- 메모리 (R4): 메모리 용량이 많이 필요한 애플리케이션용 -> 고성능 DB, 분산 캐시, BI용 인메모리 DB
- 선응 순간 확장 (T2): 성능 순간 확장 가능, 기본 제공, 가장 많이 사용 됨
- GPU (G3, P2): 그래픽 및 일반 목적의 GPU 컴퓨팅 애플리케이션
- 높은 I/O (I2): SSD 기반의 초고속 인스턴스 스토리지 -> OLTP, 관계형/NoSQL DB, Redis 같은 인메모리 캐시, 데이터 웨어하우징
- 고밀도 스토리지 (D2): 높은 디스크 처리량, 단위당 최소의 가격

### 보안 그룹 (Security Group)

EC2 인스턴스의 **방화벽 역할**을 하며, AWS 네트워크 보안의 핵심입니다.

- **허용(Allow) 규칙만** 존재 (거부 규칙 없음)
- IP 주소 또는 다른 보안 그룹을 참조하여 규칙 지정 가능
- 인바운드(외부 → 인스턴스), 아웃바운드(인스턴스 → 외부) 트래픽을 각각 제어
- 하나의 보안 그룹을 여러 인스턴스에 연결 가능 (다대다 관계)
- 특정 리전 & VPC에 종속됨 (리전이 바뀌면 새 보안 그룹 필요)
- 인스턴스 "외부"에 위치하기 때문에, 트래픽이 막히면 인스턴스 입장에서는 원인을 알 수 없음
- 기본값: 인바운드 전체 차단 / 아웃바운드 전체 허용
- **타임아웃**이 발생하면 보안 그룹 문제, **connection refused**가 발생하면 애플리케이션 자체의 문제일 가능성이 높음
- SSH용 보안 그룹은 별도로 관리하는 것을 권장

**자주 쓰이는 포트**

- 22: SSH (Linux 인스턴스 접속) / SFTP (SSH 기반 파일 업로드)
- 21: FTP (파일 업로드)
- 80: HTTP (암호화되지 않은 웹 트래픽)
- 443: HTTPS (암호화된 웹 트래픽)
- 3389: RDP (Windows 인스턴스 접속)

**EC2 Instance Connect**: 별도의 SSH 키 다운로드/클라이언트 설정 없이 AWS 콘솔에서 바로 인스턴스에 접속할 수 있는 기능. Amazon Linux 2에 기본 제공되며, 사용하려면 22번 포트는 여전히 열려 있어야 함

### 과금 옵션 및 비용 최적화

- **On-Demand**: 약정 없이 쓴 만큼만 지불 -> 갑작스러운 트래픽, 예측이 어려운 단기·중단 없는 워크로드
- **Reserved**: 1년 또는 3년 약정으로 최대 72% 할인 -> 항상 사용 중인 안정화된 서버 자원(예: DB)에 적합
  - 인스턴스 유형, 리전, 테넌시, OS 등 속성을 예약
  - 결제 방식: 후불 / 부분 선결제 / 전액 선결제 (선결제 비율이 높을수록 할인율 상승)
  - **Convertible Reserved Instance**: 인스턴스 유형·패밀리·OS 등을 변경할 수 있는 대신 할인율이 조금 낮음(최대 66%)
- **Savings Plans**: 1년/3년간 시간당 사용 금액(예: $10/h)을 약정하고 그 한도까지 할인, 초과분은 On-Demand 요금 적용 -> 특정 인스턴스 패밀리·리전에 고정되지만 인스턴스 크기, OS, 테넌시는 유연하게 변경 가능
- **Spot**: 남는 자원에 대한 경매 방식으로, 최대 스팟 가격을 설정해두면 현재 스팟 가격이 그보다 낮을 때 인스턴스를 획득. 최대 90% 저렴하지만 현재 가격이 최대 가격을 넘으면 2분의 유예 후 중지/종료됨 -> 배치 작업, 데이터 분석 등 실패에 탄력적인 워크로드에 적합, 중요 작업이나 DB에는 부적합
  - **One-time Request**: 요청이 이행되면 인스턴스가 시작되고, 이후 요청은 소멸되어 재시작되지 않음
  - **Persistent Request**: 유효 기간 동안 요청이 계속 살아있어 인스턴스가 중지되거나 가격이 올라도 조건 충족 시 자동 재시작
  - 요청을 취소해도 이미 생성된 인스턴스는 종료되지 않으므로, 완전히 종료하려면 요청 취소 후 인스턴스도 별도로 종료해야 함
  - **Spot Fleet**: Spot(+선택적으로 On-Demand) 인스턴스의 집합으로, 여러 런치 풀(인스턴스 유형/OS/AZ 조합) 중 조건에 맞는 곳에서 목표 용량을 자동으로 채워줌
    - `lowestPrice`: 최저 비용 풀 우선 (짧은 워크로드에 적합)
    - `diversified`: 여러 풀에 분산 (가용성 우수, 긴 워크로드에 적합)
    - `capacityOptimized`: 용량 확보가 가장 쉬운 풀 우선
    - `priceCapacityOptimized`(권장): 용량이 충분한 풀 중 최저가 풀 선택
- **Dedicated Host**: 물리 서버 자체를 통째로 전용 할당받는 가장 비싼 옵션. 규정 준수 요구사항이나 소켓/코어/VM 단위 라이선스(BYOL) 활용에 유용
- **Dedicated Instance**: 전용 하드웨어에서 실행되지만 같은 계정의 다른 인스턴스와 하드웨어를 공유할 수 있고, 물리 서버 자체에 대한 가시성/제어권은 없음
- **Capacity Reservation**: 특정 AZ에 필요한 기간만큼 On-Demand 용량을 예약. 약정 기간이 없어 자유롭게 생성/취소 가능하지만, 요금 할인은 없고 실행 여부와 무관하게 On-Demand 요금이 부과됨 (Reserved Instance/Savings Plans와 결합 시 할인 가능)

> 리조트에 비유하면: On-Demand는 그때그때 방을 잡고 전액 지불, Reserved/Savings Plans는 장기 숙박 약정으로 할인, Spot은 빈 방 경매, Dedicated Host는 건물 전체 예약, Capacity Reservation은 묵지 않아도 방값을 내는 예약이라고 볼 수 있습니다.

### Public IP vs Private IP

네트워크 주소는 IPv4(예: `1.160.10.240`, 약 37억 개, 현재 거의 고갈)와 IPv6(예: `3ff3:1900:4545:3:200:f8ff:fe21:67cf`, IoT 대응을 위해 등장) 두 체계로 구성됩니다.

- **Public IP**: 인터넷 전체에서 고유, 지리적 위치 파악 가능, 동일 주소 중복 불가, 인터넷에 직접 접속 가능
- **Private IP**: 프라이빗 네트워크 안에서만 고유, 위치 식별 불가, 다른 회사가 같은 대역 사용 가능, 인터넷 접속 시 NAT/인터넷 게이트웨이 필요
- EC2 인스턴스는 기본적으로 **프라이빗 IP(내부 AWS 네트워크용)**와 **퍼블릭 IP(인터넷용)**를 함께 가짐
- SSH 접속은 외부에서 들어오므로 퍼블릭 IP로만 가능하며, 인스턴스를 재시작하면 퍼블릭 IP가 바뀔 수 있음

**Elastic IP (탄력적 IP)**

- 인스턴스를 중지 후 재시작하면 퍼블릭 IP가 바뀌는 문제를 해결하기 위해, 삭제하지 않는 한 계속 소유할 수 있는 고정 퍼블릭 IPv4
- 한 번에 하나의 인스턴스에만 연결 가능, 계정당 기본 5개 제한(요청 시 증설 가능)
- 장애 발생 시 다른 인스턴스로 빠르게 재매핑해 대처 가능
- 남용하기 쉬워 AWS는 오히려 사용을 지양하고, 대신 **DNS 이름**을 붙이거나 **로드 밸런서**를 앞단에 두어 퍼블릭 IP 자체를 노출하지 않는 방식을 권장

### Placement Groups (배치 그룹)

EC2 인스턴스가 물리적 인프라에 어떻게 배치될지를 제어하는 전략입니다.

- **Cluster**: 모든 인스턴스를 동일 랙 · 동일 AZ에 배치 -> 인스턴스 간 10Gbps급 저지연 네트워크 확보. 하드웨어 장애 시 전체가 동시에 영향을 받는 것이 단점. 빅데이터 처리처럼 빠르게 끝내야 하고 지연시간·처리량이 중요한 작업에 적합
- **Spread**: 모든 인스턴스를 서로 다른 하드웨어(여러 AZ에 걸칠 수도 있음)에 배치 -> 동시 장애 위험을 낮춰 고가용성 극대화. 대신 AZ당 최대 7개 인스턴스로 제한되어 확장성이 낮음. 각 인스턴스를 격리해야 하는 중요 애플리케이션에 적합
- **Partition**: 여러 파티션(독립된 랙 세트)에 인스턴스를 분산, 파티션끼리는 랙을 공유하지 않음 -> AZ당 최대 7개 파티션, 최대 100개 인스턴스까지 운영 가능해 장애 영향은 격리하면서도 대규모 운영이 가능. 다만 파티션 하나가 죽으면 그 안의 인스턴스는 함께 영향을 받음. HDFS, HBase, Cassandra, Kafka 같은 분산 시스템에 적합

### Elastic Network Interface (ENI)

VPC 안의 **가상 네트워크 카드**를 나타내는 논리적 구성 요소로, 다음 속성을 가질 수 있습니다.

- 기본 프라이빗 IPv4 주소 1개 + 보조 프라이빗 IPv4 주소 1개 이상
- 퍼블릭 IPv4 주소 1개, 프라이빗 IPv4 주소당 탄력적 IP 1개씩 연결 가능
- IPv6 주소 1개 이상
- 하나 이상의 보안 그룹, 그리고 MAC 주소
- EC2 인스턴스와 독립적으로 생성해두었다가 필요할 때 즉시 연결하거나, 장애 조치를 위해 다른 인스턴스로 옮길 수 있음
- 단, **특정 가용 영역(AZ)에 고정**되므로 다른 AZ로는 이동 불가

### EC2 Hibernate (최대 절전 모드)

인스턴스 상태를 정리하면 다음과 같습니다.

- **Stop**: EBS 데이터는 유지되어 다음 시작 시 그대로 사용 가능
- **Terminate**: 루트 EBS 볼륨까지 삭제되어(설정에 따라) 데이터가 모두 사라짐
- 일반적인 재시작 과정은 OS 부팅 -> User Data 실행 -> 애플리케이션 실행 -> 캐시 구성 순으로 진행되어 시간이 꽤 걸림

**Hibernate**는 종료 시점의 **RAM 상태(인메모리 상태)를 그대로 루트 EBS 볼륨에 기록**해두었다가, 다시 시작할 때 OS를 처음부터 부팅하지 않고 그 상태에서 바로 복구하는 방식입니다. 부팅 시간을 크게 단축할 수 있어 실행 시간이 길고 메모리 상태를 유지해야 하는 프로세스, 초기화에 시간이 오래 걸리는 서비스에 유용합니다.

- 지원 인스턴스: C3/C4/C5, I3, M3/M4, R3/R4, T2/T3 등
- RAM 최대 150GB까지 지원, 베어메탈 인스턴스는 미지원
- 지원 AMI: Amazon Linux 2, Ubuntu, RHEL, CentOS, Windows 등
- 루트 볼륨은 반드시 **EBS(암호화 필수)**여야 하며, 인스턴스 스토어는 지원하지 않음
- On-Demand, Reserved, Spot 인스턴스 모두에서 사용 가능
- 최대 절전 유지 기간은 최대 60일

### EBS Volume

**EC2 인스턴스가 실행 중일 때 연결할 수 있는 네트워크 드라이브**로, 인스턴스가 종료된 후에도 데이터가 유지될 수 있습니다.

- 물리 디스크가 아니라 **네트워크 기반 스토리지**라서 약간의 지연이 발생할 수 있음
- 특정 **가용 영역(AZ)에 종속**됨 -> us-east-1a의 EBS 볼륨은 us-east-1b의 인스턴스에 연결 불가 (다른 AZ로 옮기려면 먼저 스냅샷을 떠야 함)
- 하나의 인스턴스에 여러 EBS 볼륨을 붙일 수 있지만, 하나의 볼륨을 여러 인스턴스에 동시에 붙이는 것은 기본적으로 불가 (io1/io2의 Multi-Attach 예외)
- 할당한 용량(GB)과 IOPS 기준으로 과금되며, 프리티어는 월 30GB(SSD 또는 마그네틱) 제공
- 볼륨 용량은 나중에 늘릴 수 있음(스케일링 가능)

**Delete on Termination 옵션**

- 루트 볼륨: 인스턴스 종료 시 **기본적으로 함께 삭제**
- 추가로 연결한 볼륨: 인스턴스 종료 후에도 **기본적으로 보존**
- 콘솔/CLI에서 이 옵션을 꺼두면 종료 후에도 루트 볼륨을 보존할 수 있음

### EBS 스냅샷 (Snapshot)

EBS 볼륨의 **특정 시점 백업**입니다.

- 볼륨을 분리하지 않고도 생성 가능하지만, 데이터 정합성을 위해 분리 후 생성하는 것을 권장
- 다른 가용 영역이나 리전으로 복사(이전) 가능
- **EBS Snapshot Archive**: 아카이브 티어로 옮기면 최대 75%까지 비용 절감 가능하지만, 복원에는 24~72시간이 소요됨 -> 장기 보관용 비용 최적화에 사용
- **Recycle Bin**: 스냅샷을 실수로 삭제하는 것을 방지, 보존 기간을 1일~1년으로 설정 가능하며 삭제된 스냅샷도 복구 가능
- **Fast Snapshot Restore (FSR)**: 스냅샷에서 볼륨을 처음 사용할 때 발생하는 초기화 지연(latency)을 없애주는 기능, 추가 비용 발생

### AMI (Amazon Machine Image)

소프트웨어, 설정, OS, 모니터링 도구 등을 미리 패키징해두어 **더 빠른 부팅과 설정**을 가능하게 하는 EC2 인스턴스의 커스터마이징 이미지입니다.

- **Public AMI**: AWS가 제공
- **Custom AMI**: 직접 만들고 관리
- **AWS Marketplace AMI**: 서드파티/유료 이미지
- 특정 리전에 종속되지만 다른 리전으로 복사 가능

**생성 과정**

1. 필요에 맞게 EC2 인스턴스를 시작하고 설정
2. 데이터 정합성을 위해 인스턴스를 중지(Stop)
3. AMI 빌드 (내부적으로 EBS 스냅샷 생성)
4. 새 AMI로 인스턴스를 launch

### EC2 Instance Store

호스트에 물리적으로 연결된 디스크를 사용하는 **고성능 임시 블록 스토리지**입니다.

- EBS보다 뛰어난 I/O 성능 제공
- 인스턴스를 **중지, 최대 절전, 종료**하면 데이터가 초기화됨(휘발성)
- 버퍼, 캐시, 스크래치 데이터 등 임시 데이터 용도에 적합
- 하드웨어 장애 시 데이터가 유실될 수 있어 백업/복제는 사용자 책임
- 즉, 최고 성능을 얻는 대신 데이터 영속성은 보장되지 않음

### EBS Volume Types

**SSD 계열**

- **General Purpose SSD (gp2/gp3)**: 저렴하면서 낮은 지연시간 -> 부팅 볼륨, 가상 데스크톱, 개발/테스트 환경에 적합. 크기 1GiB~16TiB
  - gp3: 기본 3,000 IOPS / 125MiB/s, 최대 16,000 IOPS / 1,000MiB/s까지 용량과 무관하게 독립적으로 확장 가능
  - gp2: 작은 볼륨은 최대 3,000 IOPS까지 버스트 가능, 최대 16,000 IOPS, GB당 3 IOPS 비율(5,334GB에서 최대치 도달)
- **Provisioned IOPS SSD (io1/io2)**: IOPS 일관성이 중요한 미션 크리티컬 애플리케이션, 16,000 IOPS 이상이 필요한 DB 워크로드에 적합. 크기 4GiB~16TiB
  - Nitro 인스턴스: 최대 64,000 PIOPS, 그 외 인스턴스: 최대 32,000 PIOPS (용량과 무관하게 IOPS 독립 설정 가능)
  - io2는 io1과 동일한 가격에 더 높은 내구성과 GiB당 IOPS 제공
  - **io2 Block Express**: 크기 4GiB~64TiB, 서브 밀리초 지연, IOPS:GiB 비율 1000:1로 최대 256,000 PIOPS까지 지원
  - io1/io2는 **Multi-Attach** 지원

**HDD 계열** (부팅 볼륨으로 사용 불가)

- **Throughput Optimized HDD (st1)**: 빅데이터, 데이터 웨어하우스, 로그 처리용, 크기 125GiB~16TiB, 최대 처리량 500MiB/s, 최대 500 IOPS
- **Cold HDD (sc1)**: 자주 접근하지 않는 아카이브 데이터용, 가장 저렴, 크기 125GiB~16TiB, 최대 처리량 250MiB/s, 최대 250 IOPS

> **부팅 볼륨으로 사용할 수 있는 것은 gp2/gp3, io1/io2 뿐입니다.**

**EBS Multi-Attach (io1/io2 계열)**

- 같은 AZ 안의 최대 **16개 EC2 인스턴스**가 하나의 볼륨에 동시에 연결 가능
- 연결된 모든 인스턴스가 완전한 읽기/쓰기 권한을 가짐
- Teradata 같은 클러스터형 Linux 애플리케이션의 가용성을 높이거나, 동시 쓰기 작업을 관리하는 데 사용
- **클러스터 인식 파일 시스템**이 필요 (XFS, EXT4 같은 일반 파일 시스템은 사용 불가)

### EBS 암호화

암호화된 EBS 볼륨을 생성하면 다음이 한꺼번에 암호화됩니다.

- 저장 데이터(볼륨 내부), 전송 중 데이터(인스턴스 ↔ 볼륨), 모든 스냅샷, 암호화된 스냅샷에서 만든 볼륨
- 암/복호화는 투명하게 처리되며 지연 영향은 미미
- KMS가 생성한 키를 이용한 AES-256 암호화 사용

**기존에 암호화되지 않은 볼륨을 암호화하려면**

1. 기존 볼륨의 스냅샷 생성
2. 스냅샷을 암호화 옵션과 함께 복사
3. 암호화된 스냅샷으로 새 EBS 볼륨 생성
4. 원래 인스턴스에 암호화된 볼륨 연결

### Amazon EFS (Elastic File System)

**여러 가용 영역에 걸친 다수의 EC2 인스턴스에 마운트할 수 있는 관리형 NFS 네트워크 파일 시스템**입니다.

- Multi-AZ 지원, 매우 뛰어난 확장성
- gp2 대비 약 3배 비싼 프리미엄 가격, 사전 프로비저닝 없이 사용한 만큼 과금
- NFSv4.1 프로토콜 사용, 보안 그룹으로 접근 제어
- **Linux 기반 AMI에서만 사용 가능** (Windows 미지원)
- KMS를 이용한 저장 데이터 암호화 지원
- 표준 API를 제공하는 POSIX 파일 시스템, 자동으로 용량이 확장됨
- 콘텐츠 관리, 웹 서빙, 데이터 공유, WordPress 등에 활용

**성능**

- 수천 개의 동시 NFS 클라이언트를 지원, 10GB/s 이상의 처리량
- 사전 프로비저닝 없이 페타바이트 규모까지 자동 확장

**Performance Mode**

- **General Purpose**(기본값): 지연시간이 가장 짧음 -> 웹 서버, CMS에 적합
- **Max I/O**: 지연시간은 늘지만 처리량과 병렬성이 뛰어남 -> 빅데이터, 미디어 처리에 적합

**Throughput Mode**

- **Bursting**: 1TB당 50MiB/s, 필요 시 100MiB/s까지 버스트
- **Provisioned**: 저장 용량과 무관하게 처리량을 직접 지정 가능 (예: 1TB 저장에 1GiB/s 처리량 설정)
- **Elastic**: 워크로드에 따라 자동 조정, 읽기 최대 3GiB/s·쓰기 최대 1GiB/s까지 지원 -> 예측하기 어려운 부하에 적합

**Storage Class**

- **Standard**: 자주 접근하는 파일용
- **Infrequent Access (EFS-IA)**: 저장 비용은 낮지만 조회 시 비용 발생, 라이프사이클 정책을 켜야 사용 가능, 최대 90% 이상 비용 절감 가능
- 가용성/내구성 기준으로는 **Standard**(Multi-AZ, 운영 환경용)와 **One Zone**(단일 AZ, 개발 환경용, 기본적으로 백업 활성화, One Zone-IA와 결합 가능)으로 구분

### EBS vs EFS

- **EBS**
  - 한 시점에 하나의 인스턴스에만 연결(Multi-Attach 예외), 특정 AZ에 종속
  - gp2는 디스크 크기에 비례해 IOPS 증가, io1은 독립적으로 IOPS 조절 가능
  - 다른 AZ로 옮기려면 스냅샷 생성 -> 대상 AZ에 스냅샷 복원 -> 새 볼륨 생성 과정이 필요
  - 백업 시 IO를 많이 사용하므로 트래픽이 많은 시간대는 피하는 것이 좋음
  - 루트 볼륨은 인스턴스 종료 시 기본적으로 삭제(옵션으로 끌 수 있음)
  - 실제 사용량과 무관하게 할당한 드라이브 크기 기준으로 과금
- **EFS**
  - 여러 AZ에 걸쳐 수백 개의 인스턴스가 동시에 마운트 가능 (예: WordPress 같은 파일 공유 워크로드)
  - Linux(POSIX)만 지원
  - EBS보다 비싸지만 사용한 만큼만 과금, EFS-IA로 추가 절감 가능

> 정리하면: 단일 인스턴스의 블록 스토리지가 필요하면 **EBS**, 여러 인스턴스가 파일을 공유해야 하면 **EFS**, 최고의 I/O 성능이 필요하고 데이터 유실을 감수할 수 있다면 **Instance Store**, 부팅 볼륨은 **gp2/gp3, io1/io2**만 가능하다는 점을 기억하면 됩니다.
