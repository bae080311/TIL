# SRE(Site Reliability Engineering)란?

- 구글에서 시작된 운영 방식으로, 운영 문제를 소프트웨어 엔지니어링으로 해결하는 것을 말합니다
- "서비스가 얼마나 안정적이어야 하는가"를 숫자로 정하고, 그 목표를 지키도록 시스템과 프로세스를 만드는 역할입니다
- 개발팀은 빠르게 기능을 내보내고 싶고, 운영팀은 안정성을 위해 변경을 줄이고 싶어 하는데, 이 충돌을 숫자(에러 예산)로 조율합니다

# SLI / SLO / SLA

## SLI(Service Level Indicator)

- 서비스 상태를 측정하는 지표입니다
- 예: 요청 성공률, 응답 시간(p99 latency), 가용 시간 비율

## SLO(Service Level Objective)

- SLI에 대한 내부 목표치입니다
- 예: "한 달 동안 요청 성공률 99.9% 이상"

## SLA(Service Level Agreement)

- 고객과 맺는 약속으로, 지키지 못하면 보상(환불 등)이 따릅니다
- 보통 SLO보다 느슨하게 잡습니다 (SLO가 먼저 깨져야 대응할 시간이 생기기 때문)

# 에러 예산(Error Budget)

- 100% - SLO 만큼 허용되는 실패량입니다
- 예: SLO가 99.9%면 한 달(30일) 기준 약 43분까지 장애가 허용됩니다
- 예산이 남아 있으면 → 새 기능 배포, 실험을 적극적으로 진행합니다
- 예산을 다 쓰면 → 배포를 멈추고 안정성 개선에 집중합니다
- 100% 가용성은 목표로 삼지 않습니다. 비용이 기하급수적으로 늘고 사용자는 그 차이를 체감하지 못하기 때문입니다

# 토일(Toil) 줄이기

- 토일: 수동적이고 반복적이며 자동화할 수 있는데 서비스 가치는 늘리지 않는 운영 작업입니다
- 예: 매번 손으로 하는 배포, 서버 재시작, 로그 확인
- SRE는 업무 시간의 일정 비율(구글은 50%) 이하로 토일을 제한하고 나머지는 자동화 등 엔지니어링에 씁니다

# 모니터링과 장애 대응

- 모니터링의 4가지 골든 시그널: 지연 시간(Latency), 트래픽(Traffic), 에러(Errors), 포화도(Saturation)
- 알람은 사람이 실제로 조치해야 하는 상황에만 울리게 합니다 (알람 피로 방지)
- 장애가 끝나면 포스트모템(Postmortem)을 작성합니다
  - 누구 탓인지가 아니라 왜 일어났는지, 재발을 어떻게 막을지에 집중합니다 (Blameless)
